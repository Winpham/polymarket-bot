## 0. THE TWO CORE POSITIONS, IN ONE PARAGRAPH EACH

**Designer A — the Direct Path.** Adopt the official SDK, wrapped in a new `clob-exec` crate behind a **cargo feature** (`live-exec`, default off) so that with the feature off, `alloy` is *not even compiled* — upgrading the repo's `off ⇒ never spawned ⇒ byte-identical` guarantee to `off ⇒ not compiled`. Default execution posture: **`capped_chase`** on `favorite` (rest +1¢, δ_max 2¢, 5-min cancel), **`maker_rest`** on weather, **take-or-skip split on price** for the router — all derived from one scalar claim: *the arms diverge because of `p`, since the fee is `feeRate×(1−p)` and the spread is `3.4¢/p`, both blowing up as `p` falls.* Detectors: slippage EWMA first (it can actually fire), P&L CUSUM in shadow until ≥40 day-clusters. **Designer B — the Rethink Path.** *Downloaded and read the SDK source.* Finds **there is no client-order-id and `metadata` is never echoed back** — so A's idempotency scheme is unimplementable. Replaces it with **single-flight-per-token** (a Postgres partial unique index) **+ GTD-always, never GTC** — which makes reconcile-by-token *complete* and makes a forgotten order *expire on its own*. Reframes the execution question from **maker vs taker** to **now vs later**: the ask decays 3.4¢→0.6¢ by +15min *unconditionally and outcome-blind*, and **waiting has no adverse selection because you always fill** — so **`patient_take(15m)`** captures 2.8¢ for a `tokio::time::sleep`, worth "$32/day, the single largest number in this build," with no resting order, no cancel race, and no fill model. Proves the brief's **P&L CUSUM cannot police `weather_fav` at any tuning**. Replaces it with **ΔCLV vs a matched placebo pool**. Persists only the halt latch and **replays** equity/peak from the fill ledger. **Refuses to build any maker fill model at all** — "an open question beats a biased answer."

## 2. THE ADJUDICATED CONTRADICTIONS

### 2.1 Idempotency without a client-order-id — **THE highest-stakes question in the build**

**A said:** put the key in `metadata: bytes32`; the exchange echoes it back; reconcile is a hash-join. **B said:** I read the source; it is never echoed back; that plan is unimplementable.
**I read the source. B is right.** *(A conceded it might be, and flagged it as blocking. It was.)*

**⇒ VERDICT: `refined`, but built on B's primitive.** "Double-send is impossible" is reconstructed from **three** things, none of which needs an exchange-side key:

1. **INV-1 — single-flight per token**, a Postgres partial unique index: `UNIQUE (token_id) WHERE state IN ('INTENT','SENT','LIVE','CANCEL_REQ')`. **This is the load-bearing line of the entire build.** It makes B4 (re-quote overlap) a *constraint violation*, and it makes **reconcile-by-token COMPLETE**: on restart, any open order on token T **is ours**, because we could never have sent a second one. *The key was never needed; the **uniqueness** was.*
2. **INV-2 — GTD always, never GTC** (`expiration` is NOT NULL; `CHECK (order_type IN ('GTD','FAK'))`). **An order we forget about cannot rest forever. It expires.** This neutralises the orphan catastrophe **without depending on reconcile working at all** — it holds even if the process never comes back up. *(And `post_only` requires GTC/GTD, so GTD is also the only TIF compatible with a maker leg. The constraints agree.)*
3. **The rule that kills B2 and B3 simultaneously: state NEVER advances on an HTTP response — only on a WS event or a reconcile read.** The POST's 200 is a hint. The cancel's 200 is a *request, not a fact*.

Plus: **`ON CONFLICT (client_order_key) DO NOTHING`** (our own DB double-write guard — which is *all* a client key can honestly give us), the **two-empty-reads-≥120s-apart** grace (A's, and load-bearing against `OrderStatusType::Delayed`), and **"a failed read HALTS; we never infer absence from a failure."**

**The one thing the brief got wrong that mattered most:** it asserted structural idempotency via a client-order-id. **There isn't one. The plan says so, and rebuilds the guarantee from uniqueness + expiry instead.**

Naming them separately created the illusion that the arms need *different code*. **They need different numbers.** One state machine, one set of I1–I10 tests, three rows in a table. **This part is settled.**

**But they picked different winners, and BOTH proofs failed verification:**
- **A's `capped_chase` default** rests on D31 (*"resting beats taking by +2–4% on filled signals"*) — whose own verdict is **INDETERMINATE-BY-POWER** (N=20, 2 day-clusters vs the 5 required) — and on a spread extrapolation that was never measured below p=0.75 (**A-router-1**).
- **B's `patient_take` default** is the **retracted latency lever** (**B-patient-1**: +2.05¢ ± 4.0¢, **p = 0.36**, placebo drifts MORE) and contains a self-inflicted adverse-selection hole in its own freshness gate (**B-patient-2**).
- **And B's own critique of A is correct and unanswerable:** *"maker ROI **on filled signals** vs taker ROI compares a selected subset to a full sample — the fill is a POST-TREATMENT VARIABLE. That is structurally identical to the error that produced retraction #4."* On the gate's own metric (ROI-on-**turnover**), **abstentions do not raise ROI — they only lower turnover** — and the maker policy as measured *fails* while the taker *passes*.

**⇒ VERDICT: `refined`. The seed default is `take_at_fire` — the ONLY policy whose cost is actually measured (+3.4¢, and the champion's honest ROI was computed against it).** Everything else runs as a **$0 shadow counterfactual** and earns its way in:

### 2.3 Edge-decay detection without whipsaw — **the crux**

**Verified: the brief's own detector cannot work.** P&L is the noisiest possible observable, and on `weather_fav` (20 cities, one heat dome, **ICC ≈ 1 ⇒ N_eff = 1 ⇒ day-SD ≈ 28.9%**) a **total edge collapse is a 0.19σ shift**. At `k = 0.5` that is **below the reference value** ⇒ the CUSUM statistic drifts to zero ⇒ **it never fires.** Drop `k` to 0.1 to make it fire and **ARL₀ collapses to 60 days** — false-halting a healthy arm every two months while taking 27 days to catch a real break. **The false-alarm rate is 2.2× the true-detection speed. That is not a detector; it is a coin flip with a spreadsheet.** *(B's proof. It is the sharpest piece of statistics in the forge, and it kills A's CUSUM too — A's ARL₁ = 10.4 d is the detection time for a **1σ** decay, a quantity larger than the entire edge.)*

**Does a non-P&L observable really have more power? — VERIFIED, with corrections.**

- **Slippage EWMA (the FILL detector). YES, and it is the one that will actually fire.** Slippage is observable **per order** (n ≈ 20–40/day, not 1/day) and is **not confounded by outcome variance** (measured at fill time, before resolution). ~20× the observations. **And the most probable quiet death is the fill degrading, not the pick decaying.** *But **both designers' σ₀ are uncalibrated and differ by 2.2×**, and the book-walk is size-dependent ⇒ **it ships in SHADOW until ≥100 real fills at the relevant size.*** Once armed: `λ=0.1`, `L=3.0` ⇒ ARL₀ ≈ 85 days, ARL₁ ≈ 11 orders (**under one trading day**). **Safe to arm at that ARL₀ *only because its response is DE-SIZE, not HALT*** — a false alarm costs ~$0.08/day in expectation; an undetected +1σ slippage degradation costs ~19% of the entire edge, forever. **Detector confidence sets response severity. That is the organising principle of the whole ladder.**
- **ΔCLV vs a matched placebo (the PICK detector). YES — but not for B's stated reason.** B's claim that the placebo pool "supplies σ₀ on day one" is **wrong** (the placebo controls the *mean*, not the day-level *variance*). **The real, sufficient argument: ΔCLV needs NO FILLS, so it is computable retrospectively on 395 historical signals TODAY, while real-fill ROI has n = 0 historical observations.** *That* is why one is calibratable and the other is not. **⇒ It ships with a PRE-REGISTERED FALSIFIER** (Phase 0.4): estimate `E[Δ]` and **day-cluster** `σ₀` on the 395 historical favorites vs an M=200 matched placebo pool; **if `SNR_day(ΔCLV)/SNR_day(P&L) < 2.0×`, the detector is PERMANENTLY LOG-ONLY** and the plan states plainly: *"we cannot detect selection decay on weather in under ~2 months, and no proposed detector can. We bound the loss. We do not pretend to detect it."*

**The false-demotion rate on a HEALTHY arm** — the question the brief demanded a number for:
| detector | response | ARL₀ | false-demotion cost |
|---|---|---|---|
| Slippage EWMA (`λ=0.1, L=3.0`) | **de-size (halve)**, auto-restores after 40 clean orders | ~85 days | **~$0.08/day expected.** Negligible. |
| ΔCLV CUSUM (`k=0.5, H=5.0`, burn-in `H=6.5` for 20 clusters) | **halt the arm**, human re-arm | **~939 days ≈ 1 per 2.6 years** | Sticky, but 1-in-2.6-years buys a 3–13 day detection. |
| **P&L CUSUM on `weather_fav`** | — | **N/A** | **NEVER ARMED, AT ANY n.** It cannot fire on the failure it exists to catch. |
| Day-clustered ROI **LB** crossing 0 | demote one rung (live→paper); keep accruing at $0 | slow **by design** | P&L is the **confirmation, not the alarm.** |

### 2.7 The shadow A/B — **a refusal, and it is the right call**

### 2.8 N_eff vs "the cluster IS the bet"

**A ports `independence_sizing.py`'s `N_eff = nominal/(1+(m̄−1)·ICC)` with a pre-registered ICC. B asserts the unit instead: if the game is the bet, the cap applies to the game — no ICC needed.**

**Same answer on the case that matters** (20-city heat dome, $10k bankroll): both give **$200 = 2% of bankroll**, vs the naive policy's **$1,000 = 10% on a single coin flip** — which would trip the **15% max-DD halt in one bad day, on an arm that may be perfectly healthy.**

**⇒ VERDICT: `rethink` (B).** The formula's only job on the cases that matter is to compute `N_eff = 1` — i.e. to *rediscover that a heat dome is one bet.* **Assert the unit instead of estimating it. A parameter you never introduced cannot be wrong** — and this codebase's defining failure mode is parameters that turned out to be wrong (A's own `icc = 0.90 / 0.15` are admitted, unmeasured priors). Kept from A: the `SELECT … FOR UPDATE` serialization inside the `INTENT` transaction (otherwise two concurrent signals on the same dome both read "budget available" and both deploy).

**The cheaper-to-be-wrong rule, and it must be a comment in the `super_event` port: MERGE clusters when in doubt; NEVER SPLIT.** Merging over-constrains (safe). Splitting over-deploys (dangerous) — and a naive `condition_id`-based key splits.

**And the reframe that matters:** the cluster governor is **simultaneously a RISK control and a WHIPSAW control**, and it is the **ex-ante bound on open exposure** that makes it safe for the max-DD latch to operate on *lagging realized equity* (**A/B-kill-1**). **It is the piece of this build that most directly serves Tue's "never negative for extended time" — not by detecting anything, but by making the worst single day survivable.**

### 2.9 KillSwitch persistence

**A persists the whole struct** (equity, peak, day_pnl, day, lambda) **and then warns at length about a subtle restore trap** — `KillSwitch::new()` calls `evaluate()`, which **re-latches `MasterOff` on top of the restored reason**, silently rewriting the halt cause in the audit log.

**B's insight is better: the trap exists only because the design persists a CACHE.** `equity`/`peak`/`day_pnl`/`day` are **pure functions of the realized-fill ledger** — *measurements, not decisions*. Persisting them creates a second source of truth that can drift from the first, **which is the exact class of bug this project keeps having.**

**⇒ VERDICT: `hybrid`, B's architecture. PERSIST THE DECISION; REPLAY THE MEASUREMENT.** One table (`executor_halts`, with `cleared_at IS NULL` = latched), one fact, and **the I6 audit log for free** (A needs a *second* table for it). The atomic latch is a **partial unique index** (`one_open_halt_per_arm`): two concurrent halt causes race, the **first wins**, and the log records the **first** reason, not the last to overwrite. Equity/peak are rebuilt by feeding the arm's realized fills through the **same `on_fill()` the live path uses** ⇒ **the reconstruction CANNOT drift from the runtime, because it IS the runtime.** **There is no restore trap to fall into, because there is no restore.**

**And the thing that makes it non-negotiable:** *the autoupdater recreates the container on every merge; a container recreate is a KillSwitch reset; **therefore MERGING THE EXECUTOR IS THE VERY EVENT THAT WOULD ERASE THE EXECUTOR'S HALT STATE.*** ⇒ **`executor_halts` MUST ship in the SAME PR that wires the executor. Not the next one. The same one.** Both designers said this independently and both are right.

**There is no `unhalt()` method.** Un-halting is a human `UPDATE … SET cleared_at = NOW(), cleared_by = 'human:tue'`. **The absence of the method is the design.**

## 3. THE KEY INSIGHTS THAT EMERGED (what someone reading this in three weeks needs to know)

1. **The brief's central safety mechanism does not exist.** There is **no client-order-id** on Polymarket V2, and the `metadata` field you *can* stamp is **never echoed back**. "Double-send is impossible" had to be **rebuilt from scratch** — out of a Postgres partial unique index (single-flight per token) and an order type (GTD). **The heart of the build turned out to be three lines of DDL and one enum variant.**

2. **A trade can FAIL after it MATCHES.** `TradeStatusType { Matched, Mined, Confirmed, Retrying, Failed }`. Booking on `MATCHED` books trades that never settled. **Risk counts the match; the ledger counts the confirmation.** Neither the brief, the dossier, nor the Diagnostic knew this.

3. **The P&L detector the brief asked for is structurally incapable of firing on the arm we most want to protect.** On `weather_fav` a **total edge collapse is a 0.19σ day-shift** (N_eff = 1) — *below the CUSUM's own reference value*. It cannot fire. Tune it so it can, and it false-halts a healthy arm every two months. **The detector had to move upstream of P&L, to CLV and to slippage.**

4. **Every single-number claim in this forge that lacked a placebo turned out to be fragile.** A's cost derivation double-counts. A's router proof extrapolates a spread it never measured. B's $32/day headline is a **retracted lever** (p = 0.36 *with* a placebo). **The project's own evidence rule — control arm, significance test, n + dispersion — caught all three, applied to the designers themselves.** *That rule was earned by four retractions. It works. Use it on yourself.*

5. **The two levers that could actually double the business are BOTH unmeasured, and BOTH are cheap to measure.** The maker leg (worth **+$47–61/day**, unknowable before Rung 2, resolved by a **$1 order**) and `patient_take` (worth **+$33/day**, resolved by **pure SQL, at $0, before any executor code is written**). **The entire net business today is ~$19–33/day.** ⇒ **Phase 0 is not preamble. Phase 0 is where the money is.**
